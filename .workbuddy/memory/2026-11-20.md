## 首屏加载提速 + 音乐交互按钮 + 模型并进加载条（11:0x）

**实测基线**（CDP 无头，冷缓存）：FCP 152ms（但会在 220ms ~ 1.35s 之间随机跳）、
首个长任务 915ms（建场+首次渲染）、模型请求直到 **+1359ms** 才发出。

**改动**
1. `vendor/three/three.module.min.js`（655KB / gzip 163KB）替换未压缩版（1.27MB / 252KB）。
2. `<head>` 加整张依赖图的 `modulepreload`（three、addons、src 各模块、vision_bundle）。
3. 模型请求提前：
   - `src/modelPreload.js`（新，只依赖 3KB 的 assetLoader）作为独立入口写在 head 里；
   - 外加 `<link rel=preload as=fetch crossorigin="anonymous">` → 实测 **+13~21ms** 就发出。
   - **坑**：preload 的凭据模式必须和 fetch 一致。`fetch(..., credentials:'omit')`
     与 `crossorigin="anonymous"`（CORS + same-origin）不匹配 → 7.6MB 被下两遍。
4. `assetLoader`：IndexedDB 读盘改成和网络竞速（60ms 上限）。原来是先 await IDB，
   冷启动几百毫秒，模型请求白等到 +1.3s。
5. `nextPaint()` = `rAF(() => setTimeout(r, 0))`：原来的 `rAF(() => r())` 让 await 的后续
   仍在同一帧、绘制之前执行，紧接的长任务把这一帧吞掉 → FCP 随机跳。改完稳定 236~272ms。
6. 三段文字特效（LoveMessage/CallDanmaku/LikeBurst）改动态 import + `requestIdleCallback`
   延后构建，tick / 手势事件 / 快捷键 / resize 全部判空。
7. 首屏进度条合并两件事：场景 55% + 模型 45%，文字显示「正在唤醒手势模型 42%」；
   树可看后出现「不等模型了，先看看树」，15s 超时也自动放行。
8. 默认音乐**不再偷偷自动播放**：载入后亮底部胶囊「♪ 点击播放音乐」；窄屏（≤760px）
   胶囊会压住左侧提示条 → 改为给顶栏「播放」按钮描金边（`.btn.nudge`）。
   任意点击/按键只恢复 AudioContext，开播必须用户明确点。
9. 音乐加载挪到首屏之后，不和模型抢带宽。

**实测结果**：模型请求 +1359ms → **+13ms**；热启动（immutable + IDB）模型 1452ms/5.7MB → **353ms/0 字节**；
FCP 抖动消失；遮罩收起时进度条到 100% 且手势确实可用。

**验证**：CDP 无头 Chrome — 慢网（3Mbps）下进度条显示「正在唤醒手势模型 7%」+ 跳过按钮可点；
点播放后 `audio.playing === true`、胶囊消失；t/6/l 三段特效均正常触发；无 pageerror。

## 首屏加载界面补齐（数字 / 文案 / 动效）

用户反馈「进度条没有数字、状态文本、动效」。原实现只有一条 190px 的纯色条 + 一句文案。

1. **HTML**：`.loading-status` 一行两栏 —— 左 `#loadingText`（带呼吸点），右 `#loadingPct`
   （`#loadingPctNum` + 小号 `%`）。进度条满宽（inner 420px），高 4px。
2. **数字**：`pushPct()` 只进不退（下载分片重试会回跳），`stepPct()` 每帧 `shown += d*0.17` 补间，
   `tabular-nums` 防抖动。条宽仍由 CSS transition 驱动（0.45s），和补间时间尺度接近，视觉同步。
3. **文案分级**：唤醒雪夜 → 搭建舞台 → 铺开针叶 → 连接手势模型… → 下载 x.x / 7.5 MB → 准备好了。
   `setLoadingText()` 只在不同句时触发 `swap` 淡入上滑（`offsetWidth` 重排重放）。
   `onStatus` 不再抢文案：只在 `!finished && scene>=1` 时接管。
4. **动效**：填充段 `i::before` 白光 2.4s 扫过（`bar-shine`，px 位移 500 避免宽度变化影响）；
   模型阶段未知总量时轨道 `is-wait` 跑 `bar-wait` 暗金光（在 `i` 之下，只露在未填充区）。
   `prefers-reduced-motion` 全部关掉但仍保留数字与宽度变化。
5. `finishLoading()` 改为 `pushPct(100)` + 文案，淡出延迟 240 → 480ms，让 100% 被看见。

**坑**：无头 Chrome 复测时模型走了 IndexedDB 缓存 → 下载阶段一闪而过，必须每次清 profile
（`shutil.rmtree(PROFILE)`）才能截到下载中画面。

## 音乐改成流式播放（原来整首下完才播）

用户问「现在是怎么加载的？正常音频应该边播边加载吧？为什么这么慢」。

**旧实现**：`loadUrl` 先 `fetch` 成 Blob（走 `/__audio` 代理时，serve.py 还会 `resp.read(48MB)`
把整个文件读进内存再吐）→ 判断大小 → `decodeAudioData` → 才 `play()`。
三步串行，等于「等整首 + 解码完」才出声。默认那首 2.27MB，源站实测首字节 13 秒、
60 秒只下 57KB，旧实现永远播不出来。

**新实现**（`AudioEngine.loadUrl` 重写）：
1. 直接把 URL 挂 `<audio>`，只 await `loadedmetadata`（开头几十 KB），`mode='element'` 流式。
2. 三条路按快→稳串行尝试：
   - `direct-cors`：`crossorigin="anonymous"` + `linked=true`（COS / 配了 CORS 的 CDN，频谱可读）
   - `proxy`：`/__audio`（serve.py 改成透传 Range + 64KB 边收边发，仍是流式）
   - `direct-plain`：不带 crossorigin，能出声但 `analysable=false`
3. 单条 8 秒超时；`cancel()` 用令牌 `_seq` 作废旧加载；整体 14 秒 guard。
4. 删掉 `_readBlob`；`load(file)` 本地文件仍走 buffer 解码。

**serve.py**：`_serve_audio` 重写为 Range 透传（`open_remote_audio`）+ 64KB 流式转发，
转发 `Content-Range` / `Accept-Ranges`；无 Content-Length 时 `Connection: close`。

**并发坑（重要）**：两次 `loadUrl` 并发时，后一次的 `_ensureEl` 会 `_dropEl` 掉前一次的元素，
前一次的 `_waitMeta` 既收不到 `loadedmetadata` 也收不到 `error`，只能干等 15 秒超时。
→ `_dropEl()` 里主动 reject `_pendingReject`；`loadUrl` 用 `_seq` 令牌，被取代立刻抛 `cancelled`。

**UI**：流式没有下载百分比 → 弹窗按钮「正在连接…」（不再编百分比）；
5 秒没元数据 → 顶栏「网络较慢，仍在连接音乐…」+ 按钮「网络较慢，仍在连接…」；
14 秒 → 主动 cancel + 可重试。

**验证**（限速 300KB/s 的 mock CDN，40s/1.76MB）：
元数据 652ms 到，只缓冲 5.2s 就开始播；3s 后 buf 25.3 < dur 40，仍在播。
真实源：5.7s 时 cur=4.28 / buf=8.2 / dur=141.8 → 缓冲 8 秒就出声。
无 CORS → 自动降级 proxy，analysable=true，频谱 low/rms 有值；并发第二次加载 130ms 内结束。

**COS 要点**（已写进 README）：存储桶配 CORS（GET/HEAD、Expose `Content-Length,Content-Range,Accept-Ranges`）、
公共读、`Accept-Ranges: bytes`；`appConfig.js` 的 `DEFAULT_MUSIC` 换一行即可。

## 首屏加载：等「手势真的能用」再收遮罩

**问题**：只等 `modelPrefetch` 就 `finishLoading()`，进场景后摄像头小窗还在转圈、举手没反应。
用户明确要求「在外面首页就加载完毕再进入」。

**改法**（`src/main.js`）：
- 进度条从两段变三段，`BOOT_W = { scene: 35, model: 30, rig: 35 }`（按实测耗时分的）
- `bootState` 新增 `rig`（手势链路 0..1）/`rigText`（中英文案）/`rigT0`/`finished`
- `boot()` 的 race 对象从 `modelPrefetch` 换成整条 `gesturePromise`（模型 + 摄像头 + wasm + landmarker）
- race 结果区分 ok / fail / skip / timeout，收尾文案分别给「准备好了」/「摄像头未授权 · 进入音乐模式」/「手势马上可用」
- 摄像头被拒时**立即放行**（实测 2.2s 进入），不傻等 22s 超时
- 跳过按钮 `SKIP_AFTER = 4000`（别开局就劝人放弃）；总超时 `READY_WAIT = 22000`

**关键坑：进度条僵在九十几**
`createFromOptions` 没有进度回调，只有「好了没」。先试过写死台阶 `0.68/0.84`，
再拿 `Math.max(rig, est)` 取大 —— 台阶把估时曲线压死了，反而更僵（卡 94% 三秒多）。
正解：**台阶只判断「完成没」，显示值完全由时间决定**，`0.45 + 0.53 * min(1, el2/4)` 线性 4 秒爬满。
指数渐近也不行（尾巴几乎不动，正是最焦虑那几秒）。

**stepPct 补间**：差 25 分以上给 0.42 系数（否则「已下 89%」的文案会配着数字 8% 一起出现）。

**测试环境的坑（重要）**：
- SwiftShader 无头 Chrome 下 MediaPipe 初始化会把主线程堵 3.5 秒，`ticks` 从 130fps 掉到 7fps，
  `setInterval`/`Runtime.evaluate` 全被推迟 → 采样看起来像「卡死」，真机 GPU 上 init 只要 158ms
- 页面不 `Page.bringToFront` 就算后台，rAF 被节流，逐帧补间根本不跑
- 频繁 CDP evaluate 本身会拖慢 video 就绪（1.7s → 5.3s），测量必须用
  `Page.addScriptToEvaluateOnNewDocument` 在页面内自记录
- `cameraPromise.then(() => { cameraDone = true; })` 只给成功回调 → 拒绝时多一条
  unhandled rejection，两个回调都要给

**验证**：`.workbuddy/shots/boot_check.py`（两条路径 + 截图）、`boot_trace.py`（时间线）。
正常 5.96s 收起且 `gesture.ready === true`；拒绝 2.14s 收起、文案「摄像头未授权 · 进入音乐模式」。

## 修：OK 手势的爱心方向反了

`MissYou.js` 的 `drawHeart` 里 y 多取了一次负号，整颗心是倒的（尖朝上、两瓣朝下）。
参数方程 `16sin³t / 13cos t − 5cos2t − 2cos3t − cos4t` 本身是「y 向上」的：
峰值在 t≈±1（两瓣顶，y≈+11.7），谷底在 t=π（心尖，y=−17）。
canvas 的 y 向下，所以**只在算 py 时减一次**（`py = 46 - y*2.55`）就够。
另外 `sampleShape` 是按墨迹 bbox 归一并把 y 翻正的，所以画布里的方向 = 最终方向，不会被二次翻转救回来。

心口亮芯 `arc(50, 44)` 这个 44 落在两瓣凹陷（约 33）与形心（约 53）之间，翻转后依然在心口，不用改。
验证：`ok_test.py` / `ok_mobile.py`，横竖屏都是上两瓣下尖。
